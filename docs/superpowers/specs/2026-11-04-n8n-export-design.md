# Экспорт письма через n8n в формате плагина v5 — дизайн

Дата: 04.11.2026. Статус: на согласовании.

## 1. Зачем

Clickable Mail собирает письмо из блоков и сейчас сам делает HTML «для рассылки» (`src/email/mailExport.ts`): рендерит письмо
в скрытом iframe и перекладывает DOM в таблицы. Есть подозрение, что такой HTML неправильный по структуре (лишние блоки,
разметка не по правилам).

Правильная структура уже есть — её делает связка «плагин Figma → n8n». Плагин строит `plan` (описание письма элементами),
снимает картинки и шлёт JSON на вебхук; n8n заливает картинки на хостинг и узел `html_gen` собирает HTML по правилам
ручной вёрстки, которые пользователь вычищал с 06.10 по 19.10.

Цель: приложение формирует **тот же JSON, что плагин**, и отправляет его в **новую** автоматизацию n8n. Она заливает
картинки на `demo.promo`, собирает HTML тем же генератором и **возвращает его в приложение**. Пользователь выбирает формат
(ZIP, HTML, Код) и вставляет результат в сервис рассылки.

## 3. Цели, не цели, анти-цели

**Цели**
- Приложение строит `plan` v5 и `imageNodes` в формате плагина и шлёт их на вебхук новой автоматизации.
- Новая автоматизация заливает картинки на FTP и отвечает готовым HTML, собранным генератором v5.
- Окно экспорта отдаёт этот HTML в трёх форматах: ZIP, HTML, Код.
- HTML на выходе по структуре такой же, как у писем из плагина, и по виду близок к превью в редакторе.

**Не цели**
- Outlook/VML (решение 06.10 «без Outlook»).
- Отправка письма на почту из n8n.
- Свой бэкенд, авторизация, интеграция с конкретным сервисом рассылки.
- Изменения в плагине Figma и в его воркфлоу `Figma_mail_final.json`.

**Анти-цели (провал, даже если «работает»)**
- Сломать воркфлоу плагина. Он не трогается вообще.
- Хранить доступ к FTP в приложении.
- Превращать в картинку то, что по правилам должно остаться живым текстом (текст статей, фактов, футера, надписи кнопок).
- Блоки пропадают или дублируются в HTML по сравнению с превью.

## 4. Что решил пользователь (04.11)

1. Автоматизация — **новая**, отдельная от плагинной. Код воркфлоу кладём в папку `n8n/` в корне этого проекта;
   пользователь импортирует его в n8n и пришлёт адрес вебхука, который вставляется в приложение.
2. Картинки заливает **n8n** (FTP в `email_images` на demo.promo), не приложение.
3. Форматы экспорта: ZIP, HTML, Код. Пункт «Для рассылки» убирается.
4. Результат экспорта пользователь вставляет в сервис рассылки (ESP).
5. Согласовано в пересказе: правила вёрстки плагина действуют; имя картинки с отпечатком содержимого (против кэша);
   повторно не отправляем неизменённое письмо; есть «Скачать JSON» и локальный прогон генератора.

## 5. Поток

```
Редактор → «Экспорт» → формат → «Скачать/Скопировать»
  └ письмо не собиралось или изменилось с прошлой сборки?
      да → сборка:
        1. рендер письма в скрытом iframe 600px (как сейчас в mailExport.ts)
        2. планировщик: DOM + модель блоков → plan v5 + список картинок
        3. растеризация картинок → PNG/JPEG (base64)
        4. POST payload на вебхук (тот же JSON, что у плагина)
             n8n: Webhook → картинки из base64 → FTP → html_gen v5 → Respond to Webhook { html, … }
        5. результат (HTML + карта файл→URL + локальные картинки) запоминается для этой версии письма
  └ ZIP / HTML / Код из результата
```

## 6. Приложение

### 6.1. Планировщик (`plan` из письма)

Новый модуль строит `plan` по отрендеренному письму. Основа — обход DOM по реальной раскладке, как в `mailExport.ts`
(у него уже есть: скрытый iframe, координаты, вычисленные стили, растеризация через SVG foreignObject → canvas).
Отличие: на выходе не таблицы, а элементы `plan`.

Главное преимущество перед плагином: приложение **знает, что за блок** (`data-block-id` → `Block.type`, `Block.v`, `Block.data`).
Поэтому решения «что это — кнопка, баннер, ряд коэффициентов» принимаются по типу блока и разметке рендера,
а не угадываются по слоям.

**Контракт с рендерами — модель блока и явные data-атрибуты**, а не CSS-классы и вложенность DOM. Рендеры размечают
то, что планировщику нужно знать (кнопка, подложка, ряд коэффициентов, «картинкой целиком» и т.п.); геометрия и стили
берутся из раскладки. Так планировщик переживёт правки разметки превью. Какие атрибуты и как — решает исполнитель.
Фраза в `README.md` и шапке `blocks.ts` о будущей замене разметки на табличную (MJML) устарела: HTML для рассылки
теперь делает n8n, разметка рендеров остаётся разметкой превью и источником для планировщика.

**Формат `plan`** — ровно тот, что читает `html_gen` (сверяться с его кодом, он — единственный источник истины):

```
{ v:5, width:600, height, color, bg: 'bg-….png' | null, folder, title:'Mail', assets:[…], body:{ k:'stack', items:[…] }, warnings:[…] }
```

- Координаты всех элементов (`x`, `y`, `w`, `h`) — абсолютные, в px от левого верхнего угла письма 600px.
  `html_gen` считает по ним отступы (`padding-top` = разница `y`), выравнивание и ширины.
- Элементы: `text`, `img`, `hero`, `btn`, `box`, `line`, `row`, `stack`, `cols`, `grid` (`gap` можно не использовать).
  Поля — по таблице «Виды элементов» в HANDOVER §2.2 и по коду `html_gen`.
- `text`: `st` (`ff, fs, fw, c, lh, tt, ls, dec`), `runs[]` (`t`, `d` — отличия от `st`, `ln` — ссылка), `ta`, `wrap`, `lines`.
  Значения — по правилам раздела C: стек шрифта (Verdana → `Verdana, Arial, Helvetica, sans-serif`, Roboto → Arial-стек,
  Tahoma — свой стек), `#ffffff` → `#fdfdfd`, `line-height` относительный, полупрозрачный цвет смешивается с фоном,
  абзацы — отдельными строками письма.
- `color` = `theme.bg`. `bg` — файл фона (см. 6.3) или `null`, если фон письма — только цвет.
- `warnings` — то, что приложение хочет показать пользователю (например, наложение элементов). Может быть пустым.

### 6.2. Блоки → элементы плана

Таблица задаёт намерение. Где блок не подходит под строку таблицы (редкие варианты), исполнитель решает по правилам
`ПРАВИЛА_вёрстки_v5.md`: что CSS умеет — вёрсткой, что не умеет — подложкой-картинкой с живым текстом поверх, и только
если текст не отделить — картинкой целиком.

| Блок | В плане |
|---|---|
| `hero` | `hero`: весь блок (фото, хедер, дата, лига, гербы, названия команд) — одна картинка `main` (правило F, текст на баннере вшивается). Зоны клика: логотип клиента (ссылка `logoLink` или сайт клиента) и логотип лиги, если он есть в хедере (заглушка — поля ссылки у лиги нет; так делает плагин). Гербы — не зоны. Без фото — то же, картинка с прозрачностью поверх фона письма |
| `footer` | вёрстка: логотип `<img>` со ссылкой (`logo`); платёжки — одна картинка `payments` без ссылки; App Store и Google Play — **две отдельные картинки** `apple` / `android`, у каждой своя ссылка (заглушка) и alt «Download on the App Store» / «Get it on Google Play», «&» между ними — текстом; юр. тексты живым текстом; почта — `mailto`, «Отписаться» — ссылка из поля `unsub` (по умолчанию `{{unsubscribe}}`) |
| `text` | `text`-элементы (заголовок, абзацы); вариант «В рамке» — `box` с CSS-обводкой |
| `cta` | `btn`. Сплошная заливка без графики → CSS (`fill`, `border`, `r`). Градиент, блик, фигурная форма (почти все 14 вариантов) → подложка `btn` без текста + живая надпись-ссылка. Подложка снимается по видимым границам вместе с «бортиком» (тень без размытия). Одинаковые кнопки — один файл |
| `separator` | простая сплошная полоса → `line`; всё остальное (свечение, ромбы, орнамент) → картинка без ссылки |
| `odds` | ряд коэффициентов → `cols` (равные колонки, вертикальные линии — `dividers`); рамка/плашка CSS-ом, если CSS повторит; иначе подложка + живой текст |
| `recodds` | `box` (CSS-рамка/скругление) с текстом и коэффициентом; фигурные рамки (шестигранник, уголки) → подложка + живой текст |
| `timer` | картинка `timer` целиком **со ссылкой** (заглушка): `<a><img>`, как у плагина — в рассылке её меняют на живой таймер (правило G, гайд дизайнера §5). Подпись над таймером — текстом |
| `inner` | картинка с гербами/командами поверх → картинка `banner` целиком (короткие подписи вшиваются, как у матч-баннера, правило G) |
| `facts`, `bullets`, `league`, `multibet` | общая вёрстка по DOM: тексты, картинки, CSS-рамки, ряды/столбики; декор, который CSS не нарисует, — подложкой |
| `body` (скрытый тип старых черновиков) | как `bullets` |

**Ссылки (правило D):** ссылки из полей блоков (`link`, `logoLink`, `unsub`). Пустая ссылка → заглушка
`https://www.google.com/` (проверка «Пустые ссылки» в приложении по-прежнему предупреждает). Никаких `href="#"`.
Плейсхолдеры `{{name}}`, `{{brand}}`, `{{unsubscribe}}` уходят как есть — их подставляет сервис рассылки.

**Шрифт Roboto** в HTML становится Arial-стеком (правило A10). Превью в редакторе при этом остаётся с Roboto.
CSS письма (`emailCss.ts`) использует только шрифт темы (плюс Arial в значках фактов), декоративных шрифтов нет —
правило «крупный текст декоративным шрифтом → картинка» в приложении не срабатывает, весь текст остаётся живым.

### 6.3. Картинки

- **Снятие:** растеризация элемента из скрытого iframe (механизм из `mailExport.ts`: SVG foreignObject → canvas,
  ресурсы встраиваются как data URL). Масштаб **2×** (как `scale=2` у плагина), размеры в плане — в 1×.
- **Подложка без текста** (`btn`, `block`, `item`): элемент снимается со спрятанным текстом (текст прозрачный, раскладка
  не меняется), текст идёт в план живым.
- **Формат:** есть прозрачность → PNG; крупная непрозрачная (фото hero, баннер) → JPEG ~0.85; мелкие — PNG.
- **Имена** — по правилу E: `main`, `banner`, `timer`, `logo`, `btn`, `item`, `bg`, `payments`, `apple`/`android`, `block`,
  иначе slug назначения. Повторы — `-2`, `-3`.
- **Отпечаток содержимого:** к имени добавляется короткий хэш содержимого: `btn-3f9a2c.png`. Изменилась картинка —
  изменилось имя, почта не покажет старую из кэша. Одинаковые картинки (одинаковый хэш) — один файл.
- **Фон письма:** цвет — в `plan.color`; паттерн или картинка фона — отдельный файл `bg-<хэш>` **без** сплошного цвета
  (правило K, `noSolid`), высотой с письмо; `html_gen` ставит его `cover`.
  Паттерны снимаются в 2× (они лёгкие). **Фото-фон** (режим «Картинка») снимается в **1×**: PNG, если нужна прозрачность
  (прозрачность слоя < 100% или картинка не закрывает всю высоту), иначе JPEG. Если суммарный вес картинок больше 8 МБ —
  в окне экспорта предупреждение (лимит тела запроса n8n — 16 МБ, base64 добавляет треть).
- **Папка (`folder`):** `cm/<slug клиента>/<slug названия письма>-<id письма>`. `cm` — обязательный префикс приложения
  (см. 7, безопасность). Slug — как `slug()` в `code.js` (транслитерация кириллицы). На FTP это превращается в префикс
  имени файла `cm--…--…--файл` (подпапок нет).

### 6.4. Payload (тело POST)

Поля и их порядок — как `buildPayload` в `ui.html`, чтобы «Скачать JSON» из приложения и из плагина были одного вида:

| Поле | Значение из приложения |
|---|---|
| `name` | название письма (`doc.name`) |
| `fileName` | `«<имя клиента> — <название письма>»`. Нужно для правил брендов в `html_gen` (`22bet` ищется в нём) |
| `fileKey` | `null` |
| `width`, `height` | 600 и высота письма |
| `bgColor` | `theme.bg` |
| `frameFills`, `colors`, `texts`, `blocks`, `mainAutoLayout` | пустые значения, как у плагина v5 |
| `frameId` | `doc.id` |
| `plan` | план без base64 |
| `tree` | `null` (генератор его не читает) |
| `imageNodes` | `{ id, name, file, folder, width, height, bgImageData }` на каждый файл; `bgImageData` — base64 без префикса `data:` |
| `pluginVersion` | `'5.0'` |
| `referenceImage` | `null` |
| `recipientEmail` | `''` |
| `source` | `'clickable-mail'` (новое поле, плагин его не шлёт) |
| `preheader` | `doc.preheader` (новое поле, см. 7) |

### 6.5. Окно экспорта

- Список проверок и полоса веса остаются. Пока письмо не собрано — оценка веса как сейчас; после сборки — вес реального HTML от n8n.
- Карточки форматов: ZIP, HTML, Код. «Для рассылки» удаляется.
- Кнопка действия запускает сборку, если для текущей версии письма её ещё нет, и затем экспорт. Во время сборки — шаги
  («Готовлю картинки…», «Отправляю в n8n…»), кнопка заблокирована. Ошибка — понятное сообщение и возможность повторить.
- Результат сборки запоминается для версии письма (письмо не менялось — повторно в n8n не идём). Хранить в памяти достаточно.
- Предупреждения планировщика (`plan.warnings`) показываются в окне.
- «Скачать JSON» — второстепенная ссылка в окне: сохраняет ровно тот payload, что уходит в n8n (с base64).
- Вебхук не настроен (пустой адрес) — экспорт недоступен, в окне сказано почему.

### 6.6. Форматы

| Формат | Что получает пользователь |
|---|---|
| ZIP | `index.html` — HTML от n8n, где ссылки на картинки заменены на `images/<файл>`; папка `images/` — те же файлы, что ушли в n8n (из памяти приложения, не скачивать с сервера) |
| HTML | файл `.html` — HTML от n8n как есть, картинки по ссылкам на demo.promo |
| Код | тот же HTML — в буфер обмена |

Имя файла — slug названия письма (как сейчас в `exporter.ts`).

### 6.7. Адрес вебхука

Константа в одном месте приложения (через `import.meta.env.VITE_N8N_WEBHOOK_URL` с запасным значением в коде или просто
константа — на усмотрение исполнителя). До получения адреса от пользователя — пусто, экспорт показывает «вебхук не настроен».

- Экспорт ZIP/HTML/Код «как в превью» (`exportZip`, `exportHtml`, `copyHtml` в `exporter.ts`) заменяется экспортом результата n8n.

## 7. Новая автоматизация n8n

Файл: `n8n/clickable-mail.json` в корне проекта — один импортируемый JSON (пользователь против кода узлов в отдельных файлах;
так было и в плагине). Код узлов — внутри `jsCode`.

**Цепочка**
1. **Webhook** — `POST`, новый path (uuid), `allowedOrigins: "*"`, ответ через узел Respond to Webhook.
2. **Картинки** — Code: из `body.imageNodes` делает элементы с бинарными данными из `bgImageData`, mime — по расширению.
   Имя на FTP: `folder` (с `/` → `--`) + `--` + `file`, как у плагина.
3. **FTP upload** — тот же путь `/public_html/email_images/<имя>`, тот же креденшл FTP, что в плагинном воркфлоу
   (`FTP account`; после импорта пользователь выбирает его в узле).
4. **Сведение** — дождаться всех загрузок и вернуться к одному элементу.
5. **html_gen** — копия части v5 из `Figma_mail_final.json` (до `function legacyGenerate`), без старого генератора.
   Отличие от копии одно: если в `body.preheader` есть текст, в начало `<body>` добавляется скрытый прехедер
   (`display:none;max-height:0;overflow:hidden;opacity:0;mso-hide:all`). Без прехедера HTML идентичен плагинному.
   **Источник — снимок из папки плагина (состояние 20.10).** Чтобы копия не расходилась молча с генератором плагина,
   в `n8n/` лежит скрипт синхронизации: принимает путь к плагинному `Figma_mail_final.json`, вынимает v5-часть `html_gen`,
   накладывает патч прехедера и перезаписывает узел в `n8n/clickable-mail.json` (остальные узлы и служебные поля
   не трогает). Тот же скрипт в режиме проверки говорит, совпадает ли копия с источником.
6. **Respond to Webhook** — JSON: `{ ok:true, html, kb, images:[{ file, url }] }`. `url` — как его строит `html_gen`
   (`https://demo.promo/sv/public_html/email_images/` + `encodeURIComponent(префикс--файл)`).

**Обязательно**
- **Пустой список картинок** (письмо без картинок): `Split Out` по пустому массиву не даёт элементов, и цепочка не дойдёт
  до ответа. Цепочка должна доходить до `html_gen` и ответа при любом числе картинок.
- **Ошибки** (FTP, генератор): приложению уходит ответ с понятным текстом (`{ ok:false, error }`), а не обрыв соединения.
- **Безопасность имён.** Вебхук будет виден в коде страницы, значит, на него может прийти что угодно. Перед FTP:
  `folder` и `file` — только `[A-Za-z0-9._-]` (и `/` в `folder`, который превращается в `--`), без `..`;
  расширения — только `png`, `jpg`, `jpeg`, `gif`; разумный предел размера одной картинки и числа картинок.
  Иначе через имя вида `../../index.php` можно залить файл в корень сайта.
- **Не трогать чужие картинки.** `folder` обязан начинаться с `cm/`; иначе запрос отклоняется целиком. Так через вебхук
  приложения нельзя перезаписать картинки писем плагина (`<Файл>--<Фрейм>--main.png`), которые уже у получателей.
  Остаточный риск принят: зная адрес вебхука и имя файла, можно перезаписать картинку письма из приложения.
  У вебхука плагина та же уязвимость уже сейчас.
- CORS: ответ должен читаться из браузера (приложение на другом домене). Если `allowedOrigins` Webhook-узла не
  покрывает ответ Respond-узла в версии n8n пользователя — заголовок `Access-Control-Allow-Origin` ставится в Respond-узле.

**Инструкция пользователю** (в `n8n/README.md`): импорт, выбор FTP-креденшла, активация, где взять адрес вебхука,
куда его вставить в приложении.

## 8. Как проверяем

- **Локальный прогон генератора** без n8n: скрипт в `n8n/` берёт `jsCode` узла `html_gen` прямо из `n8n/clickable-mail.json`,
  подставляет `$('Webhook')` с payload из «Скачать JSON» и пишет HTML. Ссылки на картинки для просмотра подменяются
  на локальные файлы.
- **Сверка с превью** по всем 7 шаблонам для нескольких клиентов (в т.ч. 22Bet — правила бренда): скриншот превью
  редактора против скриншота HTML генератора. Блоки не пропадают и не дублируются, тексты живые там, где по правилам
  должны быть живыми, картинки на своих местах.
- **Структура HTML** выборочно по правилам B–O: таблицы с `min-width`, нет `href="#"`, у `<img>` размеры и `alt`,
  картинки без ссылки — фоном таблицы.
- **Чистые функции** (slug, имена с хэшем, стиль текста из вычисленного стиля, сборка payload) — модульные тесты
  (в проекте тестов нет; добавить vitest — решение исполнителя).
- **Сквозная проверка** — после того как пользователь импортирует воркфлоу и пришлёт вебхук: реальная отправка,
  картинки открываются по ссылкам, HTML возвращается в приложение. До этого честно писать «через n8n не проверял».

## 9. Подводные камни

- `html_gen` опирается на координаты: отступ строки = `y` элемента минус низ предыдущего. Неточные `y/h` дают «прыгающие»
  отступы. Брать прямоугольники из реальной раскладки iframe, как это уже делает `mailExport.ts`.
- `img { max-width:100% }` в шапке HTML: у `<img>` нужны явные размеры (генератор их ставит по `w/h` плана).
- Растеризация через foreignObject: картинки должны быть встроены data URL, шрифты — загружены до снятия
  (в `mailExport.ts` это уже решено: `mountHidden`, `inlineAssets`).
- Размер запроса: картинки в base64 растут на треть. Hero 2× в PNG — несколько МБ, поэтому крупные непрозрачные — JPEG.
  Лимит тела запроса n8n по умолчанию — 16 МБ.
- Время ответа: FTP-загрузки занимают секунды–десятки секунд. Окно экспорта показывает прогресс и не даёт нажать дважды.

## 10. Решения, принятые мной (проверить)

- Hero (с фото и без) — всегда одна картинка `main`; зоны клика на логотипе клиента и на логотипе лиги
  (у лиги — заглушка, поля ссылки нет; так делает плагин).
- `inner` и `timer` — картинкой целиком; `timer` — со ссылкой-заглушкой, как у плагина.
- Кнопки сторов в футере — две картинки `apple`/`android` со ссылками-заглушками (полей ссылок в приложении нет).
- Имена файлов с хэшем содержимого (вместо `?v=`, который пользователь убрал в плагине 15.10).
- Папка `cm/<клиент>/<название>-<id письма>`; n8n принимает только папки с префиксом `cm/` (защита картинок писем плагина).
- `html_gen` — снимок из папки плагина (20.10) + скрипт синхронизации, а не ручная копия.
- Планировщик опирается на модель блока и data-атрибуты рендеров, не на CSS-классы.
- Фото-фон — в 1×, предупреждение при весе картинок больше 8 МБ.
- Скрытый прехедер добавляется в HTML, если заполнен в приложении (в генераторе плагина прехедера нет).
- `referenceImage` и `tree` не отправляются (`null`): генератор их не читает, а запрос легче.
- JPEG для крупных непрозрачных картинок, PNG для остальных, масштаб 2×.
- Сборка запускается кнопкой экспорта и кэшируется по версии письма; результат хранится в памяти.
- n8n письмо на почту не отправляет.
