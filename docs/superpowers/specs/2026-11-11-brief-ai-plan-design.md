# «Собрать по ТЗ» с ИИ: план письма из любого ТЗ — дизайн

Дата: 11.11.2026. Статус: на согласовании.

## 1. Зачем

На стартовой странице есть «Собрать по ТЗ»: пользователь вставляет текст ТЗ, справа видит план письма (клиент, тип,
тема, список блоков с пометками «из ТЗ / рыба / по макету», заметки для дизайнера), жмёт «Собрать письмо» — письмо
открывается в редакторе. Разбор ТЗ сейчас — правилами по меткам (`src/brief/parse.ts`). Он понимает только знакомые
метки и ломается на реальных ТЗ: на `examples/Planbet No Deposit Freebet Sport.md` (Markdown) он потерял обе кнопки,
не увидел шаги «Как активировать бонус», оставил `**` в теме и прехедере, значение таймера отправил в текст.

Цель: ТЗ любого вида (текст, Markdown, Word) понимает языковая модель, а пользователь видит и правит **план письма
текстом**, прежде чем собрать письмо. Письмо собирается по тем же правилам, что сейчас, — как будто его собрали
из шаблонов.

## 2. Что есть (не ломать)

- `src/brief/parse.ts` — `parseBrief(text): Brief`: разбор ТЗ правилами. Промежуточная структура `Brief`
  (клиент, тип sport/casino/vip/promo, тема, прехедер, лига, матчи, секции `top/text/button/steps/timer/note/cards/
  slots/facts`, подпись VIP, заметки).
- `src/brief/build.ts` — `buildEmail(brief, clientId): { doc, plan }`: правила сборки — порядок и варианты блоков
  по макетам Figma, рыба там, где ТЗ молчит, гербы и лиги из библиотеки (`findTeam`, `findLeague`), выделение сумм
  в шагах, заметки дизайнеру, случайный стиль. `plan` — блоки с пометкой происхождения (`tz / fish / design`).
- `src/home/BriefDialog.tsx` — окно: слева textarea с ТЗ, справа план (шапка, «Блоки · N», «Для дизайнера»),
  «Собрать письмо» → черновик → редактор. Правая часть пользователю нравится — её вид сохраняем.
- n8n на `https://n8n.clickable.space`, воркфлоу экспорта `n8n/clickable-mail.json`, инструменты в `n8n/tools/`
  (запуск Code-узлов вне n8n — `runCode`, синхронизация кода узлов из файлов репозитория).

## 3. Цели, не цели, анти-цели

**Цели**
- ТЗ можно вставить текстом или загрузить файлом `.docx`, `.md`, `.txt`.
- «Составить план» — один запрос к модели через n8n; ответ — разобранное ТЗ (`Brief`).
- Из `Brief` правилами `buildEmail` получается план; он показывается в левом окне **текстом**, который читается
  как список блоков, и его можно править. Справа — живой предпросмотр плана в нынешнем виде.
- «Собрать письмо» собирает письмо **ровно по плану** (без ИИ) и открывает его в редакторе.

**Не цели**
- Модель не пишет тексты писем, не выбирает раскладку, варианты блоков и стиль — это правила кода.
- Генерация картинок; поиск гербов и лиг вне библиотеки приложения.
- Чат с моделью, правка письма голосом/подсказками в редакторе.

**Анти-цели**
- Ключ OpenRouter в коде страницы или в репозитории.
- Выдуманные моделью суммы, сроки, условия, названия, которых нет в ТЗ.
- Правки пользователя в плане молча теряются при сборке (непонятая строка должна быть видна).
- Без ИИ (n8n недоступен, лимит, ошибка) «Собрать по ТЗ» перестаёт работать.

## 4. Что решил пользователь (11.11)

1. Ключ — в n8n: новый воркфлоу ходит в OpenRouter с ключом из креденшлов n8n; приложение знает только адрес вебхука.
   `.env.local` (не в git) с `OPENROUTER_API_KEY` — только для локального сравнения моделей.
2. План — «среднее между форматом ТЗ и списком блоков»: текст, который читается как список блоков справа, правится
   прямо в левом окне. Вид правой панели — как сейчас (пример плана — §6.2, пользователь подтвердил).
3. Где в ТЗ нет текста для блока из макета — рыба и пометка дизайнеру, как сейчас. Модель ничего не придумывает.
4. Модель по умолчанию — дешёвая платная (кандидаты Claude Haiku 5.5, DeepSeek v3.2); финально — по прогону
   примеров из `examples/` на нескольких моделях, включая бесплатные.

## 5. Поток

```
Стартовая → «Собрать по ТЗ» → окно
  Левое окно, вкладка «ТЗ»: вставить текст или «Загрузить файл» (.docx/.md/.txt → текст)
  «Составить план» ──► n8n brief-plan ──► OpenRouter ──► Brief (JSON)
                       ошибка/нет вебхука ──► parseBrief (без ИИ) + пометка «план без ИИ»
  Brief → buildEmail → план-блоки → текст плана ──► левое окно, вкладка «План» (правится)
  Правая панель: разбор текста плана на лету → шапка, «Блоки · N», «Для дизайнера», непонятые строки
  «Собрать письмо» → блоки из текста плана → черновик (случайный стиль) → редактор
```

Вкладка «ТЗ» остаётся: можно поправить исходник и составить план заново (правки в плане тогда заменятся —
с подтверждением). Без ИИ план тоже составляется (как сейчас, правилами), чтобы окно работало всегда.

## 6. Приложение

### 6.1. Загрузка файла

- `.txt` — как есть. `.md` — убрать разметку Markdown (`**`, `__`, `\` перед знаками, `#` заголовков), списки
  `- ` / `* ` сохранить как строки «- …». `.docx` — текст абзацев из `word/document.xml` (JSZip уже в зависимостях),
  пункты списков — строками «- …», переносы `<w:br/>` — переводы строк.
- Встроенные картинки (`data:image/…;base64` в Markdown, картинки в `.docx`) вырезаются и заменяются пометкой
  «[картинка]» — модель их не видит, а запрос не раздувается (ТЗ Playbaze — 7 картинок на 900 КБ). Ссылки остаются.
- Тот же «обезжиренный» текст идёт и в модель, и в разбор без ИИ (вставленный текст с `**` тоже чистится).
- Размер ТЗ ограничен (порядка 20 тыс. знаков) — дальше предупреждение и обрезка.

### 6.2. Текст плана

Формат — человекочитаемый, на русском, строится из плана-блоков и разбирается обратно без ИИ:

```
Клиент: Vave
Тип: Промо
Название: Vave Friday Freebet
Тема: Пятничный фрибет для вас
Прехедер: Фрибет 10 EUR без депозита — только до воскресенья

[Hero · Только картинка]
Текст для картинки: Пятница с фрибетом / 10 EUR без депозита / Промокод: FRIDAY10

[Кнопка] Забрать фрибет

[Текст · Обычный]
Привет {{name}},
Начните выходные с подарка: фрибет 10 EUR уже ждёт вас! …
Ставьте на любимые команды и побеждайте!

[Кнопка] Получить фрибет

[Контент · Шаги] Как активировать фрибет:
- Войдите в свой аккаунт Vave
- Введите промокод FRIDAY10 в личном кабинете
- Ставьте с фрибетом 10 EUR!

[Таймер] Срок действия предложения:

[Текст · Сноска] Обратите внимание! Фрибет действует 3 дня. Полные условия — здесь. …

[Футер · Стандартный]

Для дизайнера:
- Промокод действует до воскресенья, 23:59 UTC
- Ссылка «здесь» в сноске — нужен URL от клиента
```

Правила формата:
- Шапка (`Клиент`, `Тип`, `Название`, `Тема`, `Прехедер`) — до первого блока. Клиент и тип — из списков приложения.
- Блок начинается строкой `[<Блок> · <Вариант>]` с названиями из каталога (`catalog.ts`); вариант можно опустить —
  тогда вариант по умолчанию для блока. Короткое содержимое — на той же строке (`[Кнопка] Забрать фрибет`).
- Поля блока — строки `Поле: значение`, списки — строки `- …`, абзацы текста — через пустую строку.
- В тексте плана — только содержимое, которое пользователь может захотеть поправить: тексты, подписи кнопок, шаги,
  карточки бонусов, слоты, строки фактов, матчи (команды, лига, дата), коэффициенты, ставка «Рекомендуем»,
  подпись VIP, подпись таймера, текст для картинки hero. Оформление (стиль кнопки, цвета) — не в плане.
- Строка, которую разбор не понял (неизвестный блок/вариант/поле), подсвечивается в правой панели с номером строки
  и не попадает в письмо; «Собрать письмо» при этом работает (с предупреждением).
- Пометки происхождения («из ТЗ / рыба / по макету») показывает правая панель; рыба узнаётся по тексту рыбы.
- Раздел «Для дизайнера:» в конце — заметки **из самого ТЗ** (сроки вёрстки, игроки для картинки, пуш, пометки
  модели), строки «- …», правятся и удаляются как текст. Заметки, которые следуют из блоков (картинка hero за
  дизайнером, таймер — проставить значения, гербов нет в библиотеке, рыба, примерные коэффициенты), в текст плана
  не пишутся: правая панель считает их на лету из текущих блоков, поэтому они не устаревают после правок.
- «Текст для картинки» — поле блока hero (в письме — заметка дизайнеру, как сейчас).
- Обратимость: текст плана → блоки → текст плана даёт тот же текст (поля, которые план не показывает, берутся
  из библиотеки и умолчаний заново: гербы по названию команды, лого лиги по названию и т.п.).

### 6.3. Сборка письма

«Собрать письмо» → блоки из текста плана (в порядке плана, с вариантами из заголовков) → `createEmail` клиента →
тема и прехедер из шапки → случайный стиль (как сейчас) → `doc.brief = { source, plan, notes }` → черновик →
редактор. Порядок блоков и рыбу задаёт `buildEmail` при составлении плана; при сборке правки пользователя главнее
правил (удалил блок — его нет, переставил — так и будет). Hero и футер — первый и последний (как в редакторе).

### 6.4. Окно

- Левое окно: вкладки «ТЗ» и «План»; «Загрузить файл»; «Составить план» (во время запроса — «Составляю план…»,
  отмена закрытием окна). Ошибка ИИ — строка под кнопкой и план правилами.
- Правая панель — как сейчас, источник — текст плана; плюс список непонятых строк.
- «Собрать письмо» активна, когда в плане есть хотя бы один блок.
- Вебхук ИИ не настроен — кнопка «Составить план» делает разбор правилами, подпись «без ИИ — вебхук не настроен».

## 7. ИИ: воркфлоу n8n

Файл `n8n/brief-plan.json` — отдельный от экспорта воркфлоу, импортируется так же (инструкция в `n8n/README.md`).

```
Webhook (POST, ответ узлом, CORS) → Подготовка (проверки, промпт) → OpenRouter (HTTP Request, креденшл) →
Разбор ответа (JSON → проверка схемы) → Ответ { ok: true, brief, model, usage } / Ошибка { ok: false, error }
```

- **Запрос приложения**: `{ text, source: 'clickable-mail' }` — только текст ТЗ. Модель, промпт и справочники
  задаёт воркфлоу, а не клиент: вебхук публичный, иначе через него можно гонять свои запросы на ключе.
  Длина `text` ограничена; пустой — ошибка.
- **Промпт** (в репозитории, вписывается в узел скриптом — как `sync-html-gen.ts`): роль «разбор ТЗ e-mail
  рассылки беттинг/казино-брендов в структуру», описание полей `Brief` и секций, справочники приложения (клиенты
  с id, названия лиг и команд из библиотеки, типы писем), правила: ничего не придумывать; тексты дословно из ТЗ
  (без разметки), `name`/`[NAME]` → `{{name}}`; что не идёт в письмо (сроки вёрстки, игроки, пуш) — в `notes`;
  ответ — только JSON. Пара примеров «ТЗ → JSON» в промпте — придуманные, не из `examples/`: реальные ТЗ —
  проверочный набор для сравнения моделей и приёмочных тестов, модель не должна видеть их ответы заранее.
- **Схема `Brief` расширяется** необязательными полями для того, что в ТЗ бывает, а сейчас теряется:
  коэффициенты матча (W1 / X / W2), ставка «Рекомендуем» и её коэффициент, дата/время окончания акции у таймера,
  ссылки кнопок (если в ТЗ есть URL), ссылка на картинку баннера hero (в ТЗ бывает просьба поставить готовую
  картинку по ссылке). Есть в ТЗ — идут в письмо вместо примерных значений «по макету»; нет — как
  сейчас (примерные + заметка «уточните»). Разбор правилами эти поля может не заполнять.
- **Названия команд и лиг** — как в ТЗ (их видно в письме). Справочник библиотеки в промпте нужен для подбора
  гербов и лого: модель дополнительно возвращает id команды/лиги из библиотеки, если узнала её («Реал Мадрид» →
  `real-madrid`, «Лига наций» → `uefa-nations`); нет id — подбор по названию, как сейчас (`findTeam`, `findLeague`).
- **Ответ модели** — JSON строго по схеме `Brief` (`response_format: json_schema` там, где модель поддерживает,
  иначе — JSON по инструкции и разбор с вырезанием из ```-блока). Узел «Разбор ответа» проверяет схему, чистит
  лишнее (обрезает строки, выбрасывает неизвестные секции, клиент — только из списка), пишет причину в ошибку.
- **Модель** — параметр воркфлоу (одна строка в узле), по умолчанию — победитель сравнения (§8); `max_tokens`
  ограничен, `temperature` низкая.
- **Ошибки** — всегда HTTP 200 с `{ ok: false, error }` понятным текстом (как в экспорте); таймаут запроса к модели.
- В приложении: `src/brief/ai.ts` — вызов вебхука, проверка ответа (та же схема), таймаут; адрес — как у экспорта
  (`VITE_N8N_BRIEF_WEBHOOK_URL` или константа).

## 8. Выбор модели

Скрипт `n8n/tools/eval-brief.ts`: берёт ключ из `.env.local`, прогоняет все ТЗ из `examples/` через тот же промпт
на списке моделей OpenRouter (платные дешёвые, сильная, бесплатные `:free`), сохраняет для каждой пары
«ТЗ × модель»: ответ, `Brief` после проверки, текст плана, время, токены, цену — в `n8n/out/brief-eval/` и сводку
таблицей. По сводке пользователь выбирает модель по умолчанию; её и запасную вписываем в воркфлоу.

Цены (список OpenRouter на 11.11, $ за 1M токенов вход/выход): claude-haiku-5.5 — 0.10/0.50;
deepseek-v3.2 — 0.26/0.38; gemini-3.8-flash — 0.83/4.13; claude-sonnet-5.5 — 2/10; бесплатные (`:free`) —
gemma-4-31b-it, nemotron-3.5-super-vl и др.

**Черновой прогон 11.11** (черновой промпт ~1–2 тыс. токенов, 3 ТЗ из `examples/`, грубые проверки: клиент, тема,
кнопки, шаги, таймер, сноска, матчи, лига):

| Модель | Проверки | Время | $ за ТЗ | Замечания |

## 9. Ключи и настройки

- OpenRouter: ключ — в креденшл n8n (Header Auth: `Authorization: Bearer …`). Рекомендация: лимит трат на ключе
  в OpenRouter.
- `.env.local`: `OPENROUTER_API_KEY`, `OPENROUTER_MODEL` — только для `eval-brief.ts`; в код страницы не попадают
  (без префикса `VITE_`).
- Приложение: адрес вебхука плана (`VITE_N8N_BRIEF_WEBHOOK_URL` в `.env.local` или константа в коде).

## 10. Как проверяем

- Модульные тесты: очистка `.md`/`.docx`; текст плана ↔ блоки (обратимость для всех видов блоков, непонятые строки);
  проверка `Brief` из JSON (лишнее отрезается, неизвестный клиент → null); Code-узлы воркфлоу через `runCode`
  (как `n8n/workflow.test.ts`), ответ модели подменяется записанными ответами.
- Проверочный набор — все ТЗ из `examples/` (9 шт.; ТЗ клиентов — только локально, в git их нет): записанный ответ модели → план → письмо; ключевые элементы
  на месте:
  - Planbet No Deposit — 2 кнопки, шаги ×3, таймер, сноска, текст шапки;
  - 20Bet top win Sport / Casino — тема, прехедер, кнопки, текст шапки; экспресс в тексте; слот
    с провайдером и особенностями;
  - Vave — 2 матча, UEFA Nations League, Spain – England / Belgium – Italy;
  - 22bit / BetLabel / Granawin — матч, лига, «Детали матча» строками статистики и «5 последних личных встреч»;
    у Granawin абзацы текста между строками деталей не теряются;
  - Planbet Barcelona – Villarreal — 5 фактов с выделением в начале, срок вёрстки — в заметках;
  - Playbaze Cashback — клиента нет в списке (выбор вручную), таймер, 4-й шаг
    условий, стандартный футер, картинка баннера по ссылке; ссылки на Figma/Drive — в заметках.
  VIP с подписью менеджера и карточки бонусов в примерах не встречаются — для них придуманные ТЗ по макетам шаблонов.
- Окно — браузерный тест (как `ExportDialog.browser.test.tsx`): вставка → «Составить план» (вебхук подменён) → правка
  плана → «Собрать письмо» → черновик с блоками плана.
- Сквозная проверка — после импорта воркфлоу и креденшла: реальный запрос из окна.

## 11. Подводные камни

- Ответ модели — не всегда валидный JSON или не по схеме: проверка и понятная ошибка, запасной путь — разбор правилами.
- Бесплатные модели: лимиты частоты, недоступность; `response_format` поддерживают не все.
- Публичный вебхук тратит ключ: ограничить длину ТЗ и `max_tokens`, модель — только из воркфлоу, лимит на ключе.
- Текст плана правит человек: опечатки в заголовках блоков (`[Кнопкa]` латиницей) — подсветка, а не тихий пропуск.
- Время ответа модели — секунды; окно не блокируется намертво, показывает прогресс.

## 12. Решения, принятые мной (проверить)

- Модель возвращает `Brief` (промежуточную структуру, которую уже строит разбор правилами), а не блоки письма:
  раскладку, варианты и рыбу по-прежнему задаёт `buildEmail` — письма одинаково «по макету» с ИИ и без.
- Промпт, схема и справочники — в репозитории и вписываются в воркфлоу скриптом; клиент шлёт только текст ТЗ.
- Без ИИ окно работает как сейчас (разбор правилами), ИИ — улучшение, а не обязательная зависимость.
- Загрузка файлов — без новых зависимостей (JSZip для `.docx`).
- Модель по умолчанию — claude-haiku-5.5, запасная — deepseek-v3.2 (по черновому прогону, §8).
- Заметки: из ТЗ — разделом в тексте плана; следующие из блоков — считаются на лету (§6.2).
- `Brief` расширяется: реальные коэффициенты, «Рекомендуем», окончание акции, ссылки; id команд и лиг из библиотеки
  при названиях как в ТЗ (§7).
- Примеры в промпте — придуманные; `examples/` — проверочный набор.
