# Автоматизация n8n для Clickable Mail

Здесь два воркфлоу: `clickable-mail.json` — экспорт письма в HTML, `brief-plan.json` — план письма по ТЗ через ИИ
(раздел ниже).

`clickable-mail.json` — воркфлоу, который принимает письмо из приложения (тот же JSON, что шлёт плагин Figma v5),
заливает картинки на FTP в `email_images` на demo.promo, собирает HTML генератором `html_gen` плагина и возвращает его
приложению. Письмо на почту не отправляет. Воркфлоу плагина (`Figma_mail_final.json`) он не трогает и не заменяет.

## Цепочка

```
Webhook → Подготовка картинок → Ошибка в запросе? ─да→ Ошибка → Отправить ошибку
                                     └нет→ Есть картинки? ─да→ FTP → Все загружены → html_gen → Ответ → Отправить ответ
                                                └нет──────────────────────────────────┘
```

- **Подготовка картинок** проверяет запрос: папка только `cm/…`; в именах папок и файлов только `A–Z a–z 0–9 _ -`
  и одна точка перед расширением `png`/`jpg`/`jpeg`/`gif`; содержимое — картинка того же типа (по первым байтам);
  не больше 60 картинок и 5 МБ на картинку. Вебхук виден в коде страницы, поэтому без этих проверок через имя вида
  `../index.php` или `shell.php.png` можно было бы залить исполняемый файл, а через чужую папку — перезаписать картинки
  писем плагина.
- Имя на FTP — как у плагина: `folder` с `/` → `--`, затем `--` и имя файла (`cm--20Bet--Match-dnya-e4y343j0b--btn-3f9a2c.png`).
- **Все загружены** ждёт все загрузки; если хоть одна упала — ответ с ошибкой, а не HTML с битой картинкой.
- Ответ всегда HTTP 200 с JSON: `{ ok: true, html, kb, images: [{ file, url }] }` или `{ ok: false, error }`.

## Как подключить

1. n8n → **Workflows → Import from File** → `n8n/clickable-mail.json`.
2. Открыть узел **FTP** и выбрать креденшл FTP для demo.promo (тот же, что в узле `upload img WinSCP` плагинного
   воркфлоу; в файле он записан как `FTP account`, но после импорта его надо выбрать заново).
3. Сохранить и включить воркфлоу (**Active**).
4. Открыть узел **Webhook** → вкладка **Production URL** → скопировать адрес вида
   `https://<ваш n8n>/webhook/<uuid>`.
5. Вставить адрес в приложение — одно из двух:
   - константа `DEFAULT_WEBHOOK` в `src/email/n8n.ts` (для всех, кто собирает приложение);
   - переменная `VITE_N8N_WEBHOOK_URL` в `.env.local` (только у себя; образец — `.env.example`).

Пока адрес не задан, экспорт в приложении недоступен и окно экспорта пишет «Вебхук n8n не настроен».

## Генератор `html_gen`

Код узла `html_gen` — v5-часть генератора из плагинного воркфлоу (всё до `function legacyGenerate`) ровно с двумя
отличиями: без `plan` — ошибка вместо старого генератора, и скрытый прехедер после `<body>`, если он задан в письме.
Без прехедера HTML совпадает с плагинным байт в байт.

Снимок генератора лежит в `tools/fixtures/html_gen.plugin-v5.js`. Если генератор в плагине поменяли:

```sh
# сверить (ничего не пишет; код выхода 1 — копия устарела)
node n8n/tools/sync-html-gen.ts "D:\projects\clickable\Plugin_FIGMA-MAIL_20.10.26_DEV\n8n\Figma_mail_final.json" --check
# обновить снимок и узел html_gen в clickable-mail.json (остальные узлы не трогаются)
node n8n/tools/sync-html-gen.ts "D:\projects\clickable\Plugin_FIGMA-MAIL_20.10.26_DEV\n8n\Figma_mail_final.json"
```

После обновления воркфлоу нужно заново импортировать в n8n (или вставить код узла `html_gen` вручную).

## Локальный прогон без n8n

В окне экспорта есть ссылка «Скачать JSON» — это ровно тот запрос, что уходит на вебхук. Собрать из него HTML:

```sh
node n8n/tools/run-html-gen.ts письмо.json n8n/out/письмо
```

В `n8n/out/письмо/index.html` ссылки на demo.promo заменены на `images/<файл>`, картинки лежат рядом.
Код генератора берётся из `clickable-mail.json`, то есть тот же, что работает в n8n.

## План письма по ТЗ: `brief-plan.json`

Второй воркфлоу, отдельный от экспорта. Принимает текст ТЗ из окна «Собрать по ТЗ», спрашивает модель на OpenRouter
и возвращает структуру ТЗ (`Brief`). План и письмо из неё приложение строит само.

```
Webhook → Подготовка → Ошибка в запросе? ─да→ Ошибка → Отправить ошибку
                            └нет→ OpenRouter → Разбор ответа → Отправить ответ
```

- Запрос приложения — только `{ text, source: 'clickable-mail' }`. Модель, промпт и справочники (клиенты, лиги,
  команды) зашиты в узел **Подготовка**: вебхук открыт всем, и гонять через него свои запросы на ключе нельзя.
  Пустой текст, не строка или длиннее 20 000 знаков — ошибка без обращения к OpenRouter.
- **OpenRouter** — HTTP Request с креденшлом, таймаут 60 с. Модель по умолчанию `anthropic/claude-haiku-5.5`,
  запасная `deepseek/deepseek-v3.2` (OpenRouter переключится сам, если первая недоступна); `temperature 0`,
  `max_tokens 4000`, ответ — JSON по схеме.
- **Разбор ответа**: ошибка OpenRouter (лимит, нет денег на ключе, таймаут), обрезанный или не-JSON ответ модели —
  `{ ok: false, error }` с причиной; иначе `{ ok: true, brief, model, usage }`. Ответ всегда HTTP 200.
- Один ТЗ стоит около $0.0015 и 1–3 секунды (Haiku).

### Как подключить

1. OpenRouter → **Keys** → создать ключ для Clickable Mail. Советуем сразу поставить ему **лимит трат** (Credit limit):
   вебхук публичный, лимит ограничит расходы, если кто-то начнёт слать запросы.
2. n8n → **Credentials → Add credential → Header Auth**: имя креденшла **`OpenRouter`**,
   **Name** `Authorization`, **Value** `Bearer <ключ OpenRouter>`.
3. n8n → **Workflows → Import from File** → `n8n/brief-plan.json`. Открыть узел **OpenRouter** и выбрать креденшл
   `OpenRouter` (после импорта его надо выбрать заново).
4. Сохранить и включить воркфлоу (**Active**).
5. Узел **Webhook** → **Production URL** → скопировать адрес и вставить в приложение — одно из двух:
   - константа `BRIEF_WEBHOOK` в `src/brief/ai.ts` (для всех, кто собирает приложение);
   - переменная `VITE_N8N_BRIEF_WEBHOOK_URL` в `.env.local` (только у себя).

Пока адрес не задан, «Составить план» разбирает ТЗ правилами и пишет «План без ИИ: вебхук не настроен».

### Промпт и модель

Промпт, справочники, модели и схема ответа — в `src/brief/prompt.ts` и `src/brief/schema.ts`. В узел **Подготовка**
их вписывает скрипт (между строками `// <<REQUEST` и `// REQUEST>>`):

```sh
# сверить (ничего не пишет; код выхода 1 — узел устарел)
node --import ./n8n/tools/alias.mjs n8n/tools/sync-brief-plan.ts --check
# вписать текущий промпт в n8n/brief-plan.json
node --import ./n8n/tools/alias.mjs n8n/tools/sync-brief-plan.ts
```

После этого воркфлоу нужно заново импортировать в n8n. Тест `n8n/brief-plan.test.ts` падает, если промпт в узле
не совпадает с `prompt.ts`.

### Сравнение моделей

```sh
node --import ./n8n/tools/alias.mjs n8n/tools/eval-brief.ts --models anthropic/claude-haiku-5.5,deepseek/deepseek-v3.2
```

Ключ берётся из `OPENROUTER_API_KEY` в `.env.local` (образец — `.env.example`; в git не попадает). Скрипт прогоняет
все ТЗ из `examples/` и придуманные из `src/brief/fixtures/synthetic/` через каждую модель: ответ, замечания проверки,
текст плана, время и цена → `n8n/out/brief-eval/<модель>/`, сводка — `n8n/out/brief-eval/summary.md`.
С `--record` ответы первой модели записываются для приёмочных тестов (`src/brief/accept.test.ts`): по синтетике —
в `src/brief/fixtures/answers/`, по ТЗ клиентов — в `examples/answers/`. `--only "имя ТЗ"` — только эти ТЗ.
Перезаписывать ответы стоит после правки промпта или смены модели.

**`examples/` — только локально** (в `.gitignore`: репозиторий открытый). Там ТЗ клиентов, макеты дизайнеров,
ответы модели по ТЗ (`answers/`), эталон правил сборки (`build-rules.json`) и проверки по каждому ТЗ (`checks.ts`).
Тесты на них идут, только если папка есть; в чистом клоне — синтетические ТЗ. Новое ТЗ: положить файл в `examples/`,
записать ответ (`--only "<имя файла без расширения>" --record`), добавить проверку в `examples/checks.ts`;
пока этого нет, тесты показывают ТЗ как `todo`.

Скрипты `n8n/tools/*.ts` с `--import ./n8n/tools/alias.mjs` импортируют модули `src/` так же, как приложение (`@/…`).

Тесты воркфлоу: `npm run test:unit`.
